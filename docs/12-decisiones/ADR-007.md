# ADR-007 — Alojamiento estático en CDN edge, DNS y pipeline CI/CD

## Contexto
Para cumplir `TTFB < 200 ms`, soportar 393+ reglas `301`/`410` sin penalización de rendimiento, entregar cabeceras de seguridad HTTP y ejecutar funciones serverless de formularios sin mantener un servidor WordPress, conviene alojar en una plataforma moderna orientada a sitios estáticos y edge, manteniendo operativo el entorno de demostración en Vercel sin discrepancias funcionales.

## Decisión
Desplegar la producción definitiva en **Cloudflare Pages** con build continuo desde Git en `main`, aprovechando su red edge (`TTFB < 100 ms`), soporte nativo de Astro SSG, Cloudflare Pages Functions (`functions/api/lead.ts` y `functions/tag/[[path]].ts`), y ficheros declarativos `public/_redirects` y `public/_headers` (resuelto en [[PA-006]]).

Adicionalmente (resuelto en [[PA-024]]), mantener **compatibilidad dual con Vercel** para la pre-producción (`construccionesmbl.vercel.app`) mediante `vercel.json` (sin `trailingSlash: true` para no interferir con `POST /api/lead` ni generar saltos `308`), replicando el 100 % de las reglas `301`, el rewrite `/tag/:path*` → `/api/tag` (`410 Gone`), las cabeceras HTTP de seguridad y los adaptadores `api/lead.ts` y `api/tag.ts` sobre la lógica compartida en `src/lib/server/`.

## Consecuencias
- **Corte DNS**: se coordinará con el gestor actual de WordPress garantizando que los registros `MX` del correo corporativo permanecen intactos.
- **Limpieza pública**: se retira el enlace `Webmail` del pie de página público de la web corporativa.
- **Control de paridad**: `scripts/verify-build.py` y los tests en Vitest verifican en cada compilación la sincronización exacta entre `public/_redirects`, `public/_headers` y `vercel.json`.
